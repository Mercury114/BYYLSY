# 文法解读作业实验报告参考

> 本文基于当前五个测试程序、配套输入输出文件、文法覆盖说明和评测结果整理，供报告撰写参考。心得部分建议结合本人实际修改。本文不属于评测数据，不应加入提交 ZIP。

## 一、实验内容

本课程实验以给定的 SysY 文法为基础，分阶段完成小型编译器。本次文法解读作业处于编译器实现的准备阶段，重点是阅读和分析文法，理解各语法成分的作用、组成方式、可选与重复关系，以及相关语义限制；在此基础上设计若干测试程序，使测试集合共同覆盖文法规则和常见组合。

本次共设计五个测试程序。每个程序均包含且仅包含 10 条 printf 写语句，第一条写语句输出学号 U202441730；其余输出用于观察程序数据和运算结果。测试程序按难度编号：testfile1 为唯一 A 级程序，testfile2、testfile3 为两个 B 级程序，testfile4、testfile5 为 C 级程序。

每个测试程序都有对应的输入数据文件和输出数据文件，命名形式为 testfileN.txt、inputN.txt、outputN.txt。没有读语句的 testfile1 和 testfile5 仍提供零字节的 input1.txt、input5.txt。所有输出行在换行前保留一个空格，以匹配 printf 格式串中的末尾空格。

## 二、实验设计

### 2.1 测试集合划分

五个程序采用互补的覆盖思路，既覆盖不同文法结构，也让每个用例的输出能体现相应运算结果。

| 测试程序 | 难度 | 主要设计内容 | 输入 |
| --- | --- | --- | --- |
| testfile1 | A | 通过带副作用的函数调用观察逻辑与、逻辑或的短路；同时覆盖常量、函数调用、if/else、while、break、continue、一元运算和算术运算 | 无，input1.txt 为空 |
| testfile2 | B | 一维数组、常量数组、二维数组、数组下标、一维数组形参、函数零参数和多参数调用、getint 读入及数据更新 | 4 5 6 |
| testfile3 | B | 二维数组定义与形参、二维数组整体传参、二维数组某一行作为一维数组实参、数组参数修改、二维常量数组 | 1 2 3 4 |
| testfile4 | C | 空函数体和空语句块、嵌套块、块内声明、表达式语句与空语句、无 else 的 if、void 函数和 int 函数、getint | 9 |
| testfile5 | C | 不含顶层声明和普通函数的最简编译单元；覆盖加减乘除模、括号表达式及关系和相等判断 | 无，input5.txt 为空 |

testfile1 是集合中唯一包含短路逻辑条件的程序。probe 函数每次调用都会增加全局计数 visits，因此可以从输出中判断条件右侧是否执行。0 && probe(8) 和 1 || probe(7) 的右侧应被跳过；!0 && probe(1) 的右侧应执行。这样可以区分“只出现逻辑运算符”和“实际验证了短路行为”。

testfile2 和 testfile3 用于覆盖数组语法。testfile2 的输入 4、5、6 被读入一维数组，程序输出输入值、数组求和、常量数组计算、二维数组取值和更新结果。testfile3 的输入 1、2、3、4 填充二维数组，程序分别通过二维数组形参和一维数组形参访问数据，并修改传入数组的元素。常量数组只在本地读取，没有作为函数实参传递。

testfile4 和 testfile5 负责补齐较基础的组合。testfile4 观察块结构、语句块项、空语句、表达式语句、读语句和不同形式的 return。testfile5 不读取输入，也没有顶层声明或普通函数，集中检查算术表达式的优先级以及关系、相等判断。

### 2.2 文法覆盖说明

| 文法规则或语法成分 | 覆盖程序 | 覆盖情况 |
| --- | --- | --- |

| VarDef、InitVal | testfile2 至 testfile5 | 标量、一维和二维变量；有无初值；表达式初值、一维花括号初值和二维嵌套初值 |
| FuncDef、MainFuncDef、FuncType | testfile1 至 testfile5 | int 与 void 普通函数、不同形参情况及 main 函数 |
| FuncFParams、FuncFParam | testfile2 至 testfile4 | 无形参、普通标量形参、一维数组形参、二维数组形参及多个形参 |

| LVal、PrimaryExp、Number | testfile1 至 testfile5 | 标量左值、一维和二维数组元素、括号表达式、左值表达式和整数常量 |
| UnaryExp、UnaryOp、FuncRParams | testfile1 至 testfile5 | 普通表达式、函数调用零参数/单参数/多参数、一元正号和负号、整体及部分数组实参 |
| MulExp、AddExp | testfile1、testfile2、testfile5 | 乘、除、模、加、减及组合表达式 |

| FormatString、FormatChar、NormalChar | 五个程序 | 普通 ASCII 字符、空格、%d 格式字符和 \n 转义 |

### 2.3 补充语义约束

测试程序在覆盖语法形式的同时遵守题目补充的语义要求：常量数组不作为函数参数；一元运算符不连续重复；逻辑非只出现在条件表达式中；数组维度中引用的标识符均为常量；格式字符串只使用 %d、合法普通 ASCII 字符和 \n；所有 int 函数均以 return 表达式结束；main 返回 0；整数常量不含非法前导零。

## 三、实验过程

1. 阅读题目中的 EBNF 文法及补充语义要求，先区分终结符、非终结符、可选项和重复项，并整理数组、函数形参、语句和表达式等部分的组合要求。

2. 将文法规则和常见分支整理成覆盖清单，再把覆盖任务分配到五个测试程序中。编号 1 的程序专门包含短路条件，编号 2、3 负责数组和数组形参，编号 4、5 负责基础语句、函数和表达式组合。

3. 编写各测试程序时，为每个程序安排 10 条 printf 语句。第一条统一输出学号；后续输出选择能够说明输入、数组访问、函数调用或运算结果的值。对于使用 getint 的程序，分别准备与读入次数匹配的 input 文件。

4. 根据程序执行顺序手工推导各次输出，逐项核对循环中的 break/continue、函数副作用、数组修改和条件分支。将预期结果写入 outputN.txt，并在每行末尾保留空格。

5. 对文件进行检查，确认五个程序各有 10 条 printf 写语句；input1.txt 和 input5.txt 是空文件；其余输入数据数量与 getint 调用次数一致。将 15 个规定文件直接平铺打包，不把覆盖说明或报告文件放入 ZIP。

6. 本地使用 Visual Studio C++ 编译器，以临时 scanf 实现的 getint 辅助函数编译运行五个程序，并将运行结果与预期输出逐项比较。此检查验证了测试程序的运行结果；正式提交后的课程评测结果则用于确认评测环境下的编译、运行和覆盖情况。

## 四、实验结果与分析

根据评测页面，最终提交时间为 2026 年 11 月 11 日 16:40:49，得分为 30.00，Score 为 100%，Total 状态为 RIGHT。页面 Detail 显示：“恭喜你！样例已覆盖所有语法成分！”

| 测试程序 | Status | Coverage |
| --- | --- | ---: |
| testfile1 | RIGHT | 72.0% |
| testfile2 | RIGHT | 66.0% |
| testfile3 | RIGHT | 57.0% |
| testfile4 | RIGHT | 55.0% |
| testfile5 | RIGHT | 52.0% |
| 累积结果 | RIGHT | 100% |

每个测试程序都显示 RIGHT，说明各自的编译运行结果与提供的输入输出数据一致。单个程序的覆盖率不同，是因为测试集合按职责拆分；累计覆盖率统计的是五个程序覆盖项的并集，而不是对五个百分比取平均。五个程序组合后覆盖了评测检查的全部语法成分，因此总覆盖率达到 100%。

该结果也说明输入输出文件是测试方案的一部分：程序即使覆盖了语法规则，若输入数据、输出内容或行尾空格不匹配，测试也不能得到 RIGHT。每个程序固定 10 条写语句、提供空输入文件并保留输出末尾空格，有助于避免这类格式问题。

## 五、实验心得体会

以下内容可结合实际经历改写：

通过本次文法解读作业，我认识到测试程序设计本身也需要系统分析。仅仅写出能够运行的程序，并不能保证覆盖文法中的可选项、重复项和不同语句形式。先把规则整理成覆盖清单，再把任务分配给不同测试程序，可以减少遗漏，也便于解释每个程序的作用。

这次测试中特别重要的一点是让覆盖变得可观察。例如，testfile1 不只包含逻辑与和逻辑或，还通过带副作用的函数检查右侧表达式是否按短路规则执行；数组测试则通过函数参数和修改后的输出检查整体数组与部分数组传递。这样的设计比单纯出现某个语法符号更能说明组合确实参与了程序执行。

评测结果中每个程序的覆盖率都低于 100%，但总覆盖率达到 100%。这让我进一步理解了“单个测试的覆盖率”和“测试集合的累计覆盖率”之间的区别：不同测试可以各自承担不同的语法分支，最终由集合共同覆盖完整文法。后续继续实现编译器时，我会沿用这种按模块记录覆盖点的方式，并在新增功能后补充针对性的测试。
