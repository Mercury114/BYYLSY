# 实验一：词法分析程序设计与实现（报告参考）

> 本文根据当前 `src/Compiler.java` 实现、实验文法说明和评测截图整理，可作为实验报告的内容参考。实验心得部分请结合自己的实际过程调整。报告模板未作修改。

## 一、实验内容

本实验要求依据 SysY 文法设计并实现词法分析程序。程序读取当前工作目录下的 `testfile.txt`，从源程序中识别出关键字、标识符、整数常量、格式字符串、运算符和界符等单词，并按规定的类别码输出到 `output.txt`。输出中每行包含一个单词信息，类别码与单词原始字符形式之间只保留一个空格。

本实验使用的类别码包括：`IDENFR`、`INTCON`、`STRCON`，以及 `MAINTK`、`CONSTTK`、`INTTK`、`BREAKTK`、`CONTINUETK`、`IFTK`、`ELSETK`、`WHILETK`、`GETINTTK`、`PRINTFTK`、`RETURNTK`、`VOIDTK` 等关键字类别；运算符和界符使用 `NOT`、`MULT`、`ASSIGN`、`AND`、`OR`、`DIV`、`MOD`、`SEMICN`、`COMMA`、`LSS`、`LEQ`、`GRE`、`GEQ`、`EQL`、`NEQ`、`PLUS`、`MINU`、`LPARENT`、`RPARENT`、`LBRACK`、`RBRACK`、`LBRACE` 和 `RBRACE`。

本程序除生成便于评测的类别码输出外，也保留后续分析阶段可能使用的信息：每个 token 的类别、源程序中的原始拼写、语义值和起始行号。词法分析器还提供错误信息列表接口，为后续错误处理留出扩展位置。本实验评测输入为符合文法要求的源程序，程序的当前主要目标是正确识别这些合法输入。

## 二、实验设计

### 2.1 总体结构

程序由入口类 `Compiler`、词法分析器 `Lexer`、单词记录 `Token` 和词法错误记录 `LexicalError` 组成。入口方法完成固定文件的读取、调用词法分析器、根据配置写出结果。词法分析器只负责把字符流拆分成 token，不做语法结构判断；因此它不会检查括号是否配对、表达式是否合法，也不会构造语法树。

总体处理流程如下：

```text
读取 testfile.txt（UTF-8）
        |
逐字符扫描源程序
        |
跳过空白符和注释
        |
按首字符识别标识符、整数、格式字符串或运算符/界符
        |
保存类别、原始词素、语义值和行号
        |
按需将“类别码 原始词素”写入 output.txt
```

### 2.2 Token 数据结构

`Token` 中保存四项信息：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `category` | 统一定义的类别码 | `INTCON` |
| `lexeme` | 源程序中的原始拼写，用于评测输出 | `002`（若出现在非法输入中仍保留原文） |
| `value` | 供后续阶段使用的语义值 | 整数用 `BigInteger`；标识符和符号保存字符串；格式字符串保存去掉外层引号后的内容 |
| `line` | token 起始行号，从 1 开始 | 第 5 行为 `5` |

保留 `lexeme` 和 `value` 两个独立字段是必要的。例如，整数输出应保留读入的字符形式，而不是把整数重新转换后输出；与此同时，后续语义分析又可以直接使用数值对象。格式字符串的 `lexeme` 包含两侧引号，字符串值不含外侧引号，但保留 `%d` 和 `\\n` 等转义写法，便于之后进行格式串检查。

### 2.3 词法规则与识别方法

1. **标识符与关键字**：标识符首字符为 ASCII 英文字母或下划线，后续字符可为 ASCII 英文字母、数字或下划线。扫描完整标识符后，通过关键字映射表查询类别；命中关键字时返回对应关键字类别，否则返回 `IDENFR`。这样可以保证 `main` 被识别为 `MAINTK`，而 `main1` 仍被识别为标识符。

2. **整数常量**：连续读取十进制数字，类别为 `INTCON`。原始数字串保存在 `lexeme` 中，数值通过 `BigInteger` 另行保存，避免词法阶段因机器整数范围而丢失输入值。文法规定十进制整数为 `0` 或以非零数字开头的数字串；扫描器也为多位数以 `0` 开头的情况记录词法错误信息。

3. **格式字符串**：遇到双引号后持续读取，直到配对双引号或输入结束。合法格式串中识别 `%d` 和 `\\n`，并检查普通字符范围。词素原文整体保留为 `STRCON`，不会把字符串内部的内容拆成其他 token。

4. **注释与空白**：空格、制表符和换行等空白字符不产生 token。`//` 注释跳过至行尾；`/*` 注释跳过至首次出现的 `*/`，不进行嵌套解析。扫描过程中遇到换行会更新当前行号，因此注释和空白不会影响后续 token 的行号记录。

5. **运算符与界符**：采用最长匹配原则，先检查 `&&`、`||`、`<=`、`>=`、`==` 和 `!=`，再检查单字符 token。例如，`<=` 应整体识别为 `LEQ`，不能先输出 `LSS` 再输出 `ASSIGN`。单字符 `!`、`=`、`<`、`>` 则分别识别为 `NOT`、`ASSIGN`、`LSS`、`GRE`。

### 2.4 输出及错误接口

输出由 `writeTokens` 集中完成，格式固定为：

```text
类别码 空格 原始词素
```

程序默认开启词法结果输出，以满足本次自动评测要求。通过系统属性 `compiler.tokenOutput` 可关闭这项调试输出；关闭时仍会创建或清空 `output.txt`，避免残留旧结果。后续接入语法分析器时，可以直接使用 `Lexer.scanAll()` 返回的 token 列表，并将该输出开关关闭。

`LexicalError` 保存错误类别、描述和行号，`Lexer.getErrors()` 可供后续错误处理使用。当前作业只要求处理正确程序，因此这些错误信息不会混入 `output.txt`，也不会改变合法输入的输出格式。

### 2.5 算法复杂度

扫描器从左向右遍历输入，每个普通字符只被消费一次；对固定长度的双字符运算符进行常数次比较，关键字通过哈希表查询。因此扫描时间复杂度为 **O(n)**，其中 `n` 是源文件字符数。token 列表、原始词素及语义值需要随 token 数量和输入长度增长，空间复杂度为 **O(n)**。

## 三、实验过程

1. 阅读实验题目中的类别码表，并结合文法 PDF 确认标识符、十进制常量、注释和格式字符串的基本规则，整理需要支持的关键字、双字符运算符和单字符界符。

2. 先定义 `Token` 数据结构，将类别码、原始词素、语义值和行号放在同一条记录中；再定义 `Lexer`，使它负责扫描输入、产生 token 并收集词法错误信息。

3. 按字符类型实现扫描分支：标识符扫描后查关键字表，数字扫描后建立整数语义值，双引号触发格式字符串扫描，剩余字符交由运算符和界符映射处理。注释和空白在产生 token 前统一跳过。

4. 在双字符运算符识别中采用最长匹配；在扫描注释和字符串时同时维护行号。对未识别字符、孤立的 `&` 或 `|`、未闭合注释、非法整数开头和格式串错误等情况，记录带行号的 `LexicalError`，以便后续扩展。

5. 实现固定文件接口：以 UTF-8 读取 `testfile.txt`，默认将每个 token 按类别码和原始词素写入 `output.txt`。整个过程中不把诊断信息写到标准输出，避免干扰评测结果。

6. 使用样例程序进行逐行核对，并补充接口测试，覆盖类别码、注释、起始行号、超长整数、格式字符串原文和错误记录。随后将源码单独打包，检查压缩包中的文件路径和内容。

本地兼容性检查使用 `javac --release 8 -Xlint:all` 编译源码，限制为 Java 8 API；入口为 `Compiler.main`，符合题目给出的 Java 提交入口约定。评测平台截图所示的编译命令也成功执行。

## 四、实验结果与分析

题目样例程序包含常量数组定义、主函数、变量定义、`getint` 调用、`printf` 格式字符串和 `return` 语句。程序输出的 token 顺序与题目给出的样例一致，类别码和原始拼写均逐项匹配；本地比较结果为 **38 行 token 信息一致**。

本地接口测试覆盖了类别码表中的关键字、运算符和界符，并检查了注释跳过、行号递增、整数语义值、字符串值以及错误信息行号。输出开关关闭时，`output.txt` 被清空；重新开启后，样例结果能够再次正确生成。

根据提交后的评测截图，本次作业结果为 **20.00 分，状态 Accepted**；`testfile1` 至 `testfile15` 均显示 `Accepted`，未出现不匹配项。这说明程序满足该评测集合对词法类别、token 顺序和输出格式的要求。上述结果反映的是当前作业和评测数据的验证情况，不代表词法分析器已经实现语法分析或完整编译器的错误恢复。

输出文件使用 UTF-8 写入，每行只包含类别码、一个空格和原始词素。注释和空白不输出，格式字符串作为一个整体输出，因而不会把字符串中的 `%d` 错误拆成其他单词。错误接口虽已预留，但本题仅测试合法程序，后续错误处理阶段还需要根据课程要求将错误码、错误行号与规定的报告格式连接起来。

提交包按要求只包含 `src/Compiler.java`，不包含 `.class` 文件、测试文件、报告模板或其他工程文件。运行时需将源程序命名为 `testfile.txt`，并从该文件所在目录启动程序。

## 五、实验心得体会

以下内容可结合个人实际进行改写：

通过本次实验，我对词法分析在编译器中的职责有了更具体的认识。词法分析器并不直接理解完整语句，而是按照字符和词素规则，把源程序转换为后续阶段能够使用的 token 序列。只要类别、顺序或原始词素有一处错误，就可能影响后续分析或自动评测，因此输出格式和扫描边界同样需要认真处理。

实现过程中，最长匹配原则是一个重要细节。像 `<=`、`==` 和 `&&` 这样的双字符运算符必须优先于相应的单字符符号识别。注释和格式字符串也需要单独处理：注释中的符号不能被误当成程序 token，字符串内部的逗号、括号和 `%d` 也不能被拆开。通过记录 token 的起始行号，我还为后续错误定位保留了必要信息。

我也体会到，单词的原始拼写和语义值并不总是同一件事。评测要求数字按输入形式输出，但后续阶段需要数值本身；因此在 token 中同时保存 `lexeme` 和 `value`，比只保存其中一项更适合作为编译器阶段之间的接口。完成本次测试后，评测结果全部通过，也让我确认了类别表、输出格式和固定文件名都必须严格遵守。

后续如果继续扩展编译器，我会在保留现有 token 接口的基础上接入语法分析，并把词法错误信息接入统一的错误报告机制；同时继续使用独立测试覆盖新加入的语法和异常情况。
